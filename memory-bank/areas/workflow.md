## speckit-цикл (перед нетривиальной фичей)
Если `spec.md` для фичи ещё нет:
1. `/speckit.specify` — `spec.md` по описанию задачи
2. `/speckit.clarify` — устранить пробелы/неоднозначности
3. `/speckit.plan` — `plan.md` с архитектурными решениями
4. `/speckit.tasks` — `tasks.md` (чеклист)
5. `/speckit.analyze` — проверка консистентности артефактов (ОБЯЗАТЕЛЕН)
6. Реализация по `tasks.md`

Артефакты — в `specs/<feature-name>/`. Активная фича — `.specify/feature.json` (`feature_directory`).
Шаблоны артефактов — ТОЛЬКО из Memory Bank (`resources/speckit-templates/`, см. [[speckit-templates]]),
не из generic-базы `.specify/templates/`.

**Когда speckit НЕ нужен:** баг-фикс, рефактор < 50 строк, правка конфига, обновление доков.

**Plan mode (harness) vs speckit — не путать уровни.** speckit — «режим плана» проекта на уровне
*документов*: заставляет спроектировать до кода (артефакты + форк-вопросы + обязательный `analyze`).
Harness-режим **Plan** — гардрейл, блокирующий ЛЮБЫЕ записи (`Write`/`Edit`) до выхода через
`ExitPlanMode`. Артефакт-фазы speckit (`specify`→`tasks`) **физически пишут** файлы — проходить их
внутри Plan mode НЕЛЬЗЯ (запись заблокируется). Plan mode уместен лишь на **read-only** отрезках:
разведка кодовой базы до старта спеки или чтение готового `tasks.md` перед «go» → затем выход и
запись. В `/flow` роль «стоп перед кодом» уже играют форк-вопросы + `analyze`.

**Правило clarify:** прежде чем класть параметр/поле в вектор варьирования или в контракт, убедись,
что оно РЕАЛЬНО влияет на целевое поведение — проверяй чувствительность на этапе clarify/plan, а не
постфактум через тест.

## Экономия контекста оркестратора (рост Active Context в одном цикле)

Активный контекст оркестратора растёт внутри ОДНОГО прогона (транскрипт append-only): каждый
`tool_result` и **отчёт субагента** оседают в окне до конца цикла. С ~50–60% заполнения окна модель
деградирует. Регламент сдерживания:

- **Потолок отчёта субагента ≤ ~2k токенов** + file-offload — зашит в контракт агентов
  `.claude/agents/flow-*.md`. Read-only роли (`flow-finder`/`flow-expert`) ссылаются `path:line`
  вместо дампов; `flow-builder` кладёт объёмное (полный лог/дифф) в файл, возвращает путь.
- **Бюджет-триггерный `/checkpoint`** (прокси по числу тяжёлых `tool_result`/отчётов): **~80k**
  рабочий потолок · **~120k** мягкий (checkpoint на границе пачки) · **~160k** жёсткий (сброс
  немедленно). Не чаще — компактизация рвёт prompt-cache. Пороги — `.claude/skills/checkpoint/SKILL.md`.
- **Синхронный спавн — дефолт; НЕ поллить.** Нужен результат к следующему шагу — иди синхронно
  (`run_in_background: false`). Фон — только для реально параллельной длинной работы, и тогда жди
  авто-нотификацию. Ручной поллинг `TaskList/TaskGet` в цикле — запрещён.
- **Параллельный fan-out = пиковый всплеск** (N отчётов разом) — при тяжёлых выходах последовательно
  с checkpoint между, либо субагент-редьюсер сжимает сырьё в одно резюме.
- **StatusLine-датчик** `.claude/statusline.js` (Node, кросс-ОС) показывает реальный `context_window`
  (токены/% + маркер порога) — делает бюджет измеримым.

## Recall-маршрутизация Memory Bank

Чтобы не грузить лишние заметки банка, маршрутизация — **pull через recall**, а не чтение «всё подряд»:

- **Оркестратор** перед выбором PARA-заметок прогоняет `py scripts/mb_recall.py query "<цель>"`
  (Windows; POSIX — `python3 …`) и берёт **shortlist top-k** (лексический индекс `.recall-index.json`,
  gitignored, пересобирается сам). Фолбэк при недоступном интерпретаторе — ручной выбор по
  `memory-bank/README.md`. Регламент зашит в `.claude/skills/{flow,status}/SKILL.md`.
- **Субагентам — МАНИФЕСТ путей, не контент.** В спавн-промпт идёт отфильтрованный список
  (`path` + однострочное описание), а НЕ тела заметок — субагент подтянет нужное сам.
- **Сигнал атомизации.** Периодически `py scripts/mb_recall.py atomize-signal` (exit 1 = есть
  кандидаты сверх бюджета спицы/толстые хабы) → нарезать по [[memory-regimen]]. Гейт публикации.
- Каталог команд recall — [[commands]]; полный регламент банка — [[memory-regimen]].
