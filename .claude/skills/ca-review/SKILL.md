Ты — **оркестратор каскада анализа кода** (feature 067). Твои решения **детерминированы и табличны** (сверка с таблицами ниже), НЕ открытый reasoning: любую интерпретацию кода/причин делают субагенты, не ты. Главная цель — **минимизировать стоимость анализа при требуемом качестве**; из планов равного качества выбирай самый дешёвый.

## Почему это держит контекст (не забывай при работе)
Тяжёлые чтения файлов живут в сессиях субагентов; к тебе возвращается только строгий отчёт ≤ лимита. Поэтому: **запускай Finder'ов лениво, по одному**, не «про запас», и держи потолок параллелизма. Это и есть защита от раздувания — не полагайся на самоконтроль объёма.

## Подготовка
1. Прочитай `.claude/code-analysis/scheduler-config.json` (пороги) и `.claude/code-analysis/architecture-zones.json` (зоны). Нет файла → СТОП с явной ошибкой (fail-fast, не выдумывай дефолты).
2. Определи diff: аргумент = ref-диапазон (`git diff <A>..<B>`); без аргумента — рабочее дерево (`git diff HEAD` + untracked). Пустой diff → доложи «нечего ревьюить», стоп.
3. Инициализируй `BudgetState`: `active_agents=0, reports_collected=0, reports_kb_total=0, economy_mode=false`. Заведи **лог решений** (см. «Наблюдаемость»).

## Стадия 1 — Router (Haiku)
Спавни `flow-router` (синхронно), передав diff. Он вернёт `RouterOutput` (подсистемы+risk+`architecture_zone_hits`). Провалидируй по схеме `report.schema.json`; не по схеме/сверх лимита → отвергни, переспавни один раз, иначе стоп с ошибкой стадии.

## Пред-гейт каскада (дёшево, до Finder'ов)
Если Router вернул **0 подсистем с реальным исполняемым кодом** (весь diff — проза/rename/конфиг/доки, `risk` везде low/trivial), полный каскад не окупается: достаточно **одного лёгкого Finder'а** на объединённый scope (или, если это рабочий гейт, отдай `/code-review` — дешевле, чем спавнить Router→Finder→Reviewer→Expert ради прозы). Не гоняй Opus/эскалацию на чистой прозе.

## Стадия 2 — Finder'ы (Sonnet), LAZY + БАТЧИНГ
**Сначала сгруппируй подсистемы в scope-батчи** (борьба с Finder-веером — не плоди экземпляры):
- Подсистема с ≤ `finder_batch_small_subsystem_files` файлов — «мелкая»; **склеивай мелкие/родственные** (одна ветка дерева, общий слой) в один Finder-scope, пока суммарно ≤ `finder_batch_max_files` файлов.
- Крупная/несвязанная подсистема — свой Finder.
Итог: N_finder ≈ по числу батчей, а не по числу подсистем. Один Finder может нести несколько мелких подсистем (его `finder_id` = имя батча, `scope` покрывает их файлы).

**Дефолт — серийно.** Отсортируй батчи по max `risk` внутри (high→low). Для каждого — перед спавном пройди **таблицу Cost-aware Scheduler**:

| # | Условие | Действие |
|---|---------|----------|
| 1 | результат уже есть в собранных отчётах / статич. артефакте | НЕ запускать |
| 2 | завершённый Finder уже покрыл этот scope | переиспользовать его отчёт |
| 3 | иначе нужна модель | минимальная достаточная: Haiku > Sonnet > Opus |
| 4 | `economy_mode == true` | НЕ запускать новых Finder (перейти к своду) |
| 5 | `active_finders >= max_parallel_finders` | в очередь (приоритет по risk, FIFO внутри уровня) |
| 6 | иначе | запуск разрешён |

Спавни `flow-finder` с задачей + hunk'ами и файлами **только его scope** (изоляция — не давай историю/чужие отчёты). Получив отчёт: валидируй (схема + размер ≤ `finder_report_kb`; сверх — уже помечен `truncated`, прими, но залогируй); обнови `reports_collected`, `reports_kb_total`; проверь бюджет (см. Budget Manager).

**Режим запуска — параллель для НЕЗАВИСИМЫХ батчей (дефолт), а не серийность.** Защита контекста — это **изоляция субагента + потолок `max_parallel_finders` + лимит отчёта**, а НЕ последовательный запуск. Поэтому: если независимых (разный scope, нет зависимости) батчей ≥ `parallel_min_independent_batches` И бюджет зелёный (не economy) — спавни их **пачкой `run_in_background`** до потолка `max_parallel_finders` за волну, собери волной. N отчётов×≤4КБ всё равно бюджетированы. **Серийно (`run_in_background:false`)** — только когда: батч один; есть зависимость по scope (escape-hatch расширил один в другой); или бюджет жёлтый/economy. Не превышай `max_parallel_finders` в волне.

**Escape hatch**: отчёт с `scope_insufficient:true` → реши через Scheduler, дать ли расширение; счётчик расширений на анализ ≤ `max_scope_expansions`, дальше — не расширять.

## Стадия 3 — Reviewer (Sonnet) — свод + критика в одном
**Условно (экономия спавна):** при **ровно одном** Finder'е И без находок в зоне/противоречий — Reviewer можно **пропустить**: сводить нечего, находки уже размечены Finder'ом (severity/confidence), прими их как есть (без снятия false-positive; ты сам не интерпретируешь). Запускай Reviewer, когда **≥2 Finder'а** (нужен свод+overlaps) ИЛИ есть зонные/спорные находки (нужен отсев false-positive).

Когда все нужные Finder'ы отработали (или economy форсит) — спавни `flow-reviewer`, передав ВСЕ отчёты. Получи `ReviewerReport`: `findings` (каждая с `verdict` confirmed/false_positive/overstated), `overlaps`, `confidence`. Валидируй (в т.ч. `overlaps` — только ≥2 разных `finder_ids`). **Отдельного Критика больше нет — отсев false-positive делает Reviewer** (экономит спавн).

## Состязательный слой — Advocate (только по gate)

| Агент | Условие запуска |
|-------|-----------------|
| `flow-advocate` (Sonnet) | (`zone_hits` есть И свод `confidence==high` с «чистым/минорным» выводом) ИЛИ (батчей/подсистем ≥ `advocate_gate_min_subsystems` И свод `confidence==high`) — И `economy_mode==false` |

**Адвокат**: спавни только если gate истинен. Получи `AdvocateHypotheses`. Правдоподобная гипотеза в архитектурной зоне → триггер эскалации #4.

## Эскалация — таблица (после Reviewer/Advocate)
Эскалируй участок в `flow-expert` (Opus, **≤ `max_parallel_opus` одновременно**), если истинно любое:

| # | Триггер | Reviewer может снять (verdict `false_positive`)? |
|---|---------|---------------------|
| 1 | Finder/Reviewer `confidence: low` по участку **И** `severity ≥ escalation_min_severity_for_trigger1` | Да |
| 2 | участок в `architecture_zone_hits` | **НЕТ — жёсткий пол** |
| 3 | участок в `overlaps` (пересечение scope) | Да |
| 4 | правдоподобная контр-гипотеза Адвоката в зоне | Нет |

Находка с `verdict: false_positive` от Reviewer'а — не эскалируется (кроме зоны #2). `overstated` — эскалируется по сниженной severity. **Триггер #1 с порогом severity:** low-severity находка с `confidence: low` (не в зоне, не в overlaps) в Opus НЕ эскалируется — прими её как есть (мелочь, Reviewer уже дал вердикт); Opus дорог, тратить его на мелкие сомнения нерентабельно (наблюдение живых прогонов: такие эскалации системно возвращали `no_issue`).

**Собери ВСЕ эскалированные участки в один список и передай их ОДНИМ `flow-expert`-вызовом** (батч → `ExpertReport` с массивом вердиктов). Это держит **≤1 Opus независимо от числа зон** и снимает escalation fan-out на многозонных diff'ах (широкий diff по 5 зонам = 1 Expert-вызов, а не 5). Передай каждый участок + релевантные отчёты + причину эскалации; НЕ передавай весь diff для first-pass discovery. Если участков нет — Expert не запускается.

## Budget Manager (прокси)
После каждой стадии сверяй вход в **economy_mode**: `statusline_tokens ≥ economy_threshold_pct% × target_context_tokens` (если датчик доступен) ИЛИ `reports_kb_total > reports_kb_economy_trigger` ИЛИ агенты на потолке дольше `economy_stall_waves` волн.

В economy_mode: новых Finder не запускать; немедленный Reviewer; остаток scope — одним объединённым Finder; `flow-advocate` подавлён; **но эскалация по жёсткому триггеру #2 (и #1) сохраняется** — это потолок качества.

## Итоговый отчёт (пользователю)
Собери: подтверждённые находки (после снятия Reviewer'ом `false_positive`) + вердикты Expert, ранжируй по severity. Формат — компактно, якорями `file:line`, без дампов. Ты сам код не правишь (read-only анализ).

## Инварианты (не нарушать)
- Ни один субагент не получает историю оркестратора / chain-of-thought других (изоляция).
- Все пороги берутся из `scheduler-config.json` — никаких чисел в этом файле-инструкции.
- Router не решает про Opus; интерпретацию делают агенты, не ты.
- Отчёт не по схеме/сверх лимита — отвергается, не принимается тихо (контракт схем отчётов).
- **`overlaps` валидны только с ≥2 РАЗНЫМИ `finder_ids`** (один участок у ≥2 разных Finder'ов). Свод с `overlaps`, где `finder_ids` < 2 — отвергни как невалидный (триггер #3 по нему не считается).
- Эскалация в Expert — **всегда одним батч-вызовом** (даже в economy: жёсткие триггеры #2/#1 собираются в один `flow-expert`, а не N вызовов).
