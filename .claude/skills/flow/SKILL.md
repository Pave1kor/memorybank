## User Input


Ты — **Оркестратор** команды flow (модель — **текущей сессии**, её задаёт пользователь
через `/model`; НЕ пиннится). Ты НЕ пишешь продакшн-код и НЕ проводишь глубокую
аналитику руками — ты дирижируешь: гоняешь speckit, раздаёшь работу субагентам команды,
принимаешь решения и **спрашиваешь пользователя на каждой развилке**.

(`AskUserQuestion`), не угадывай.

| Аргумент | Путь |
|----------|------|
| пусто | Продолжить **активную фичу** (`.specify/feature.json`) — путь «Реализация». |
| `new <описание>` | Завести **новую фичу** — путь «Новая фича». |
| «запиши долг …» / «запиши идею …» | **Записать** пункт в `memory-bank/projects/roadmap.md` — путь «Запись долга/идеи». Работу НЕ запускаешь. |
| название/описание существующей цели | Найти цель (фича по имени · долг · идея — по slug'у из `/status` или ключевым словам) и работать над ней — путь «Работа по цели». |

Примеры: `давай закроем долг [front-lineage]` → долг; `042` или имя фичи →

перечисли кандидатов из `/status`-ландшафта и уточни.

## Роли — единая команда flow (жёсткое разделение)

Проект использует **одну команду субагентов «flow»** (роестр `flow-*`), общую для dev-воркфлоу
и ревью-каскада `/ca-review`. Модели СПАВНИМЫХ ролей зашиты в их определениях (`.claude/agents/
flow-*.md`); модель оркестратора — сессии, не пиннится.

| Роль | Модель | R/W | Когда зовёшь |
|------|--------|-----|--------------|
| Оркестратор | сессии (`/model`) | — | ты сам: speckit-фазы, решения, синтез, вопросы пользователю, git |
| `flow-router` | Haiku | RO | триаж diff'а → подсистемы/risk/зоны (стадия 1 ревью-каскада) |
| `flow-finder` | Sonnet | RO | сфокусированный scope: research кода/данных ИЛИ поиск дефектов |
| `flow-reviewer` | Sonnet | RO | свод + критика находок ревью-каскада |
| `flow-advocate` | Sonnet | RO | состязательный recall (gated) в ревью-каскаде |
| `flow-expert` | Opus | RO | глубокая верификация / трудный read-only research |
| `flow-builder` | Sonnet | R/W | пишет/правит код по `tasks.md` (единственная пишущая роль) |

**Reasoning effort (faster↔smart) задан пер-роль** в их frontmatter (`effort:`), поверх модели:
`flow-router` low (быстрый триаж) · `flow-finder`/`flow-reviewer`/`flow-builder` medium ·
`flow-advocate`/`flow-expert` high («умные» роли — глубина окупается, они редки). Effort
**оркестратора** — сессионный (не пиннится): регулируется `/fast` и выбором модели `/model`.

Не делай руками то, что должен делать субагент: исследование → `flow-finder` (scoped) /
`flow-expert` (deep), написание/правка кода → `flow-builder`. Сам держишь план, контракт и решения.

- **Memory Bank обновляется ТОЛЬКО на `develop`** (единственный источник истины). Записи банка

## Speckit-цикл (готовые команды, ПРИВЯЗАН к flow — авто-запуск)

Фазы `specify → clarify → plan → tasks → analyze` — это **готовые команды**: скиллы
`.claude/skills/speckit.*.md` поверх **курированных шаблонов из Memory Bank**
(`memory-bank/resources/speckit-templates/` — в вариациях фронт/бэк, индекс
`resources/speckit-templates.md`; НЕ `.specify/templates/`) + обёртки
`scripts/bash/*.sh`. Они **привязаны к flow**: когда путь этого требует (новая фича или
нетривиальная цель без `spec.md`), запускай их **автоматически, по ходу**, без отдельного
вопроса «прогонять ли speckit» (это НЕ развилка — развилки только ВНУТРИ фаз, см. ниже).

**`analyze` ОБЯЗАТЕЛЕН, не опционален.** По готовности `tasks.md` ВСЕГДА прогоняй кросс-
артефактную проверку (`spec` ↔ `plan` ↔ `tasks` ↔ конституция) ДО реализации, для любой
speckit-фичи. **Находки применяй к артефактам** (правки `spec`/`plan`/`tasks`) в том же проходе;
спорные/архитектурные — выноси пользователю как развилку. К реализации переходи только с
согласованными артефактами (0 CRITICAL/HIGH). Конституция v2.1.0 закрепляет это правило.

**Как запускать в этой агент-сессии (важно).** Программный вызов speckit через `Skill`
возвращает `Unknown skill` — команды напрямую отсюда не триггерятся. Поэтому для каждой
фазы **выполняй ТОТ ЖЕ workflow инлайн**, не сочиняя свой формат:

1. Открой `.claude/skills/speckit.<phase>.md`.
2. Если в его frontmatter есть `scripts:` — прогони setup-скрипт (`setup-plan.sh` /
   `setup-tasks.sh` / `check-prerequisites.sh`). **На Windows — bash-вариант через
   инструмент Bash (Git Bash)** или зеркало `scripts/powershell/*.ps1`. Разбери его JSON
   (пути `FEATURE_DIR`/`TEMPLATES_DIR`/`AVAILABLE_DOCS`); `TEMPLATES_DIR` указывает на
   курированные шаблоны банка — сами скрипты шаблоны НЕ копируют.
3. Пройди по шагам «Outline»/«Execution flow» этого `.md` поверх **курированного шаблона из
   Memory Bank** (`memory-bank/resources/speckit-templates/<артефакт>-<frontend|backend>.md` —
   выбери вариант по домену фичи; НЕ `.specify/templates/`), запиши артефакт
   (`spec.md`/`plan.md`/`tasks.md`) в каталог фичи, обнови `.specify/feature.json` (`feature_directory`).
4. `specify` сам присваивает следующий свободный `NNN` и создаёт каталог `specs/NNN-<slug>/`.

**Развилки остаются за пользователем.** `clarify` (и `[NEEDS CLARIFICATION]` в `specify`) —
это места, где ты СПРАШИВАЕШЬ пользователя (`AskUserQuestion`) по «Инварианту развилок»,
а ответы кодируешь обратно в спеку. Автоматизирован ЗАПУСК фаз, не решения внутри них.

> Если появится нужда в родном запуске `/speckit.*` — это уже интерактивная сессия
> (пользователь набирает команду) или отдельный долг (до-родить `.ps1`-обёртки /
> регистрацию скиллов как вызываемых). В `/flow` — инлайн-путь выше.

## Ветки (переключение)

- Цель может жить на своей ветке `feat/NNN-<slug>`. Если незакрытая задача — на **другой
  ветке**, переключись на неё (`git checkout feat/NNN-<slug>`) прежде чем работать.
- **Сразу после переключения — синхронизируй фичу с `develop`** (рецепт «Синхронизация
  фиче-ветки с develop» в [[commands]]: `git fetch origin && git merge origin/develop && git
  push`). Регламенты/агенты/банк живут на `develop` — несинхронизированная ветка работает по
  УСТАРЕВШИМ правилам (возвращаются починенные баги). Конфликт → `--abort`, спроси пользователя.
- Перед переключением проверь рабочую копию: грязная и изменения относятся к текущей цели —
  закоммить их WIP на своей ветке или `git stash`; **не тащи чужие правки на другую ветку**.
  Однозначно решить нельзя — спроси пользователя.
- Ветку новой фиче заводит путь «Новая фича» (от `develop`) и сразу публикует её на сервере.

## Путь «Новая фича» (`new <описание>`)

1. **Изоляция.** Присвой следующий свободный номер (`specs/NNN-<slug>/`). Создай ветку
   `feat/NNN-<slug>` от актуальной базы (`develop`) и **сразу опубликуй её**
   (`git push -u origin feat/NNN-<slug>`) — ещё до коммитов, чтобы ветка была видна на
   сервере с самого начала. Для параллельной работы с другой фичей — заведи git worktree
   (deferred tool `EnterWorktree`), чтобы копии не толкались.
2. **Speckit-цикл** — запусти его АВТО по разделу «Speckit-цикл (готовые команды…)» выше
   (инлайн-исполнение `speckit.specify → clarify → plan → tasks → analyze`, останавливаясь
   на развилках для вопроса пользователю). Артефакты — в `specs/NNN-<slug>/`.
3. **Сделай фичу активной**: пропиши `feature_directory` в `.specify/feature.json`.
4. **После составления spec/plan/tasks — ОБЯЗАТЕЛЬНО обнови Memory Bank НА `develop`** (не только при
   завершении фичи, но и по итогам планирования). **Планируемая фича — ФАЙЛ НА ФИЧУ:** заведи
   `memory-bank/projects/planned/NNN-slug.md` (диагноз/развилки/US/статус speckit — это единственный
   develop-дом, т.к. `specs/` на фиче-ветке), а в `projects/active-context.md` добавь только
   строку-указатель `→ [[NNN-slug]]` (НЕ разворачивай блок фичи в active-context). + профильный при
   нужде (`projects/roadmap.md` — пометить долг/идею `→ фича NNN`; `resources/decisions.md` — durable
   решения из clarify). Полный регламент — [[memory-regimen]]. Правь/коммить/пушь на `develop`,
   даже если сама фича живёт на своей ветке.
5. **Реализацию не начинай автоматически** — предложи прогнать её (`/flow` без аргумента).
6. **Не коммить** без явной команды.

## Путь «Работа по цели» (название/описание) и «Реализация» (активная фича)

1. **Найди цель.** Фича — по имени в `specs/*`; долг/идея — по slug'у/ключевым словам в
   `memory-bank/projects/roadmap.md` (секции «Идеи (отложено)» / «Долги (в работе / открыто)»).
   Не нашёл там — закрытые пункты в `memory-bank/archive/roadmap-closed.md` (историческая
   справка, НЕ цель для работы). Не найдено/неоднозначно — уточни у пользователя.
2. **Оцени состояние цели и выбери режим:**
   - **Нет `spec.md` и цель нетривиальна** (новый блок / слой данных / контракт API /
     индикатор) → пройди speckit-цикл АВТО (раздел «Speckit-цикл (готовые команды…)» —
     инлайн-исполнение, по существующему номеру/ветке), сделай активной. **По готовности spec/plan/tasks — обнови Memory Bank на `develop`** (как в
     «Новой фиче» п.4), затем переходи к реализации.
   - **Есть `tasks.md`** → **реализация**: раздавай задачи `flow-builder` (по одной или
     логичными пачками по зависимостям), катясь до конца. Проверяй отчёт, проставляй `[X]`,
     обновляй затронутый Memory Bank. На границе логической пачки — вызови `/checkpoint`
     (см. раздел «Контрольные точки контекста»).
   - **Мелочь** (баг-фикс / рефактор <50 строк / конфиг / доки) → speckit пропусти, сразу
     раздай `flow-builder`, проверь результат.
3. **Останавливайся только когда:** (а) упёрся в развилку → спроси пользователя;
   (б) упали тесты → разбери и перезапусти задачу; (в) вся цель закрыта.
4. Если цель — долг/идея из roadmap: пометь пункт `→ в работе (feat/NNN)`; по закрытию —
   вычеркни/`✅`.
5. Аналитика по необходимости (шаг ниже). Скоуп цели не расширяй. Коммит/мердж/пуш — только
   по триггеру раздела «Завершение и публикация»; mid-task не коммить.

## Путь «Запись долга/идеи» (запиши долг/идею …)

Вызови `/debt <текст>` — он добавит пункт в `memory-bank/projects/roadmap.md` (долг/идея,
стабильный `[slug]`, без дублей) и запушит на `develop`. Работу НЕ запускает. Детали — в
`.claude/skills/debt/SKILL.md`.

## Аналитика (по необходимости, любой путь)

Если нужно разобраться в коде/данных прежде чем планировать/чинить — спавни исследователя
команды: `flow-finder` (Sonnet) для scoped-вопроса или `flow-expert` (Opus, ультракод) для
глубокого/трудного — с узким вопросом и режимом `research`. Получив факты+рекомендацию, вынеси
поднятые развилки пользователю.

## Завершение и публикация (когда цель закрыта)

Триггер — **вся цель доведена** (фича реализована / долг починен / идея внедрена), тесты
зелёные, открытых развилок нет. НЕ срабатывает после каждой под-задачи `Tnnn` и НЕ при
незакрытой цели — тогда просто доложи статус и остановись (незавершённую цель в `develop`
не сливай).

По триггеру вызови `/publish` — он делает ревью-гейт (`/review-gate`) → обновление Memory
Bank (+ `CLAUDE.md`/конституция, если менялись контракты/архитектура/принципы) →
избирательный коммит → мерж `feat`→`develop` → пуш, и докладывает итог. Конфликт мержа —
развилка, `/publish` остановится и спросит, не разрешай наугад. Детали процедуры и точные
git-команды — `.claude/skills/publish/SKILL.md` и каталог [[commands]] («Git-рецепты»).

Мерж `feat`→`develop` — только по этому триггеру (незавершённую цель в `develop` не
сливаем). Коммитит только оркестратор (через `/publish`); mid-task субагенты/`flow-builder`
не коммитят.

## Контрольные точки контекста (компактирование)

Длинная сессия дорожает: каждый ход перечитывает весь контекст (жжёт лимит), а с ~50–60%
заполнения окна модель заметно деградирует («тупит/зависает»). На границе **логической
пачки** подзадач (НЕ каждого `Tnnn`) вызови `/checkpoint` — он выносит состояние в
`tasks.md`/Memory Bank, выводит маркер сброса и уступает ход. Детали —
`.claude/skills/checkpoint/SKILL.md`.

- **Бюджет-триггер (прокси).** Точный размер контекста модели не виден — ориентируйся на
  прокси (число тяжёлых `tool_result`/отчётов субагентов/крупных чтений с прошлого сброса):
  **~80k** рабочий потолок, **~120k** мягкий триггер (checkpoint на ближайшей границе пачки),
  **~160k** жёсткий предел (сброс немедленно). Не чекпоинть чаще бюджета — компактизация
  рвёт 5-минутный prompt-cache. Детали порогов — `.claude/skills/checkpoint/SKILL.md`.
- **Держи тяжёлую работу в субагентах** (`flow-builder`/`flow-finder`/`flow-expert`): их контекст живёт в своём
  окне и не оседает у тебя — в основной контекст идёт только отчёт (≤ ~2k токенов по контракту).
  Главный рычаг экономии, дополняющий чекпоинты.

## Спавн субагентов

- Research: `Agent(subagent_type="flow-finder", ...)` (Sonnet, scoped) или `Agent(subagent_type="flow-expert", ...)` (Opus, deep) с режимом `research` — модели зашиты в определениях.
- Реализация: `Agent(subagent_type="flow-builder", ...)` — модель Sonnet зашита.
- Не переопределяй модель в вызове без явной причины — тиринг задан определениями агентов.
- **Субагент — одноразовый stateless-спавн (дефолтная модель).** Каждый вызов `Agent`
  стартует с чистого контекста: дай **самодостаточный промпт** (пути, факты, что вернуть).
  Нужно продолжить/уточнить — делай **новый спавн** с дистиллятом из его отчёта, а НЕ
  `SendMessage` к уже завершённому агенту. `SendMessage` годится ТОЛЬКО пока агент **ещё
  выполняется** (фоновый, финальный отчёт не отдан); ре-диспатч завершённого агента
  ненадёжен и зависает (наблюдавшийся симптом: «resumed from transcript in the background»
  → `stopped`, «no completion record»).
- **Манифест путей, не контент заметок.** В промпт субагенту передавай **манифест** — top-k
  из recall, отфильтрованный тобой (`path` + однострочное описание), — а НЕ вставленный
  текст заметок целиком; субагент откроет нужное сам через `Read`.
- **Отчёт субагента оседает в твоём контексте.** Контракт агентов держит отчёт ≤ ~2k
  токенов (тело/дампы — в файл или `path:line`); не проси субагента «выгрузить всё» —
  проси вывод + указатели. Объёмное сырьё подтягивай из файла ТОЛЬКО когда реально нужно.
- **Режим — ФОН ПО УМОЛЧАНИЮ** (правило пользователя 2026-07-15). Спавн `flow-builder`/
  `flow-finder`/`flow-expert` — `run_in_background:true`, и **жди авто-нотификацию** о
  завершении, НЕ поллить в цикле (`TaskList`/`TaskGet`/`TaskOutput` оседают в окне; само
  ожидание контекст не растит). **Почему:** синхронный спавн блокирует ход и НЕ стримит
  прогресс — многоминутная молчаливая работа субагента читается пользователем как
  «зависание»; фон не блокирует, даёт нотификацию, позволяет вмешаться. Синхронно
  (`run_in_background:false`) — ТОЛЬКО для тесных цепочек, где граница хода бесполезна (напр.
  стадии ревью-каскада `router→finder→reviewer`, когда результат нужен немедленно в том же ходу).
- **Раздавай МЕНЬШИМИ пачками, не мегабатчами.** Дели работу по US/логическим кускам (не
  «7 задач разом»): молчаливый субагент не должен молчать 10–20 мин. Независимые куски —
  параллельно в фоне до потолка волны; защита контекста — изоляция + лимит отчёта (≤~2КБ).
  **Осторожно с ветками при активном фоне:** субагент без worktree-изоляции работает в ОБЩЕМ
  рабочем дереве — НЕ переключай ветки (`git checkout`), пока фоновый агент жив (выдернешь
  дерево из-под него); переключайся только в безопасном окне (агентов нет / дерево чисто).
- **Параллельный fan-out — всплеск, но ограниченный.** N субагентов разом вернут N отчётов
  одновременно (единичный скачок), но каждый ≤ лимита — суммарно бюджетировано; держи потолок
  волны (≈3 одновременно). При очень тяжёлых выходах — либо волнами с чекпоинтом между, либо
  fan-in: сведи N сырых отчётов в одно резюме через `flow-finder`/`flow-reviewer`, а не тащи
  N сырых в окно оркестратора.

## Проактивность («Дальше:»)

По завершении любого шага/пути называй пользователю следующий логичный скилл — по
**канонической последовательности** из `memory-bank/resources/commands.md` (`[[commands]]`,
раздел «Канонические последовательности»: new-feature / work-goal / debt). Терминал, если
следующий шаг неочевиден — «цель закрыта / жди пользователя», а не молчание.
