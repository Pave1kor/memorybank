## User Input

```text
$ARGUMENTS
```

Ты проводишь **глубокий разбор** заданного вопроса. Механизм — **нативное расширенное
мышление Клода** (extended thinking), НЕ внешний инструмент: в проекте нет MCP-серверов, и
`sequential-thinking`/подобные не нужны. Думай в собственном рассуждении на максимальную
глубину (**ultrathink**), а наружу выдавай сжатый вывод.

## Принцип

Глубина — в рассуждении, не в объёме ответа. Не гадай по памяти, не срезай углы, не смешивай
проверенное с догадкой. Каждое утверждение о поведении кода/данных — подтверждай фактом
(`Read`/`Grep`/`Bash`/`pytest`), а не «вспоминай».

## Протокол (проходи по шагам)

1. **Рамка.** Сформулируй вопрос одним предложением и явно очерти границы: что входит, что
   вне охвата, какой критерий «ответ найден».
2. **Декомпозиция.** Разбей на 2–5 под-вопросов, на которые можно ответить независимо.
3. **Гипотезы.** По каждому под-вопросу выпиши **конкурирующие** объяснения/варианты
   (минимум 2, где это осмысленно) — не фиксируйся на первом.
4. **Проверка фактом.** Каждую гипотезу подтверди или отвергни по источнику истины:
   - код — `Read`/`Grep`/`Glob` с якорями `path:line`;
   - поведение — прогоном (`pytest -q <тест>`, запуск конкретного code-path), а не рассуждением;
   - внешние API — `WebFetch`/`WebSearch` (память про версии/сигнатуры врёт).
   Помечай итог: `[проверено кодом]` / `[проверено прогоном]` / `[гипотеза]`.
5. **Взвешивание.** Для выбора из вариантов — плюсы/минусы/риски каждого и **влияние на
   инварианты** проекта (`memory-bank/areas/constraints.md`). Дай явную рекомендацию, а не
   перечисление.
6. **Первопричина.** Для бага — докопайся до корня (почему, а не только где); проверь, нет ли
   более глубокой причины за первым симптомом.
7. **Само-проверка перед выводом.** Спроси себя: каждое ли утверждение подтверждено? не выдана
   ли догадка за факт? не осталось ли непроверенных допущений? Непроверенное — в раздел
   «Не проверял».

## Формат вывода (сжато)

1. **Итог** — 2–4 предложения: что выяснил, что рекомендуешь.
2. **Факты** — списком, с якорями `path:line` и пометкой уверенности (см. шаг 4).
3. **Не проверял / неизвестно** — честный короткий список. Пустой блок лучше ложной уверенности.
4. **Развилки** — неоднозначности, которые должен решить человек: «вопрос → варианты». НЕ
   решай их сам (в `/flow` это выносит пользователю оркестратор).
5. **Риски/инварианты** — что легко сломать.

Пиши на русском (язык проекта). Тело больших выгрузок в ответ не вставляй — только вывод +
указатели `path:line`.
